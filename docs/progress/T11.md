Logika eskalasi & skor frustrasi dari fase 3 menjadi rujukan T13.

## Dokumentasi OpenRouter yang diperiksa (Okt 2026)

| Hal | Temuan → implementasi |
|---|---|
| Fallback model | `models` = daftar berurutan [utama, ...cadangan]; `model` di respons = model yang melayani (biaya dihitung menurut model itu) |
| Usage & biaya | Selalu dikirim (`prompt_tokens`, `completion_tokens`, `cost`); `usage: {include: true}` sudah usang sehingga tidak dikirim |
| Atribusi | `HTTP-Referer` + `X-OpenRouter-Title` (`X-Title` hanya kompatibilitas lama) |
| Routing provider | `provider.data_collection: 'deny'` (default kita, demi privasi) terbukti jalan dengan Haiku 4.5 |
| Streaming | Komentar `: OPENROUTER PROCESSING` diabaikan; usage di chunk terakhir sebelum `data: [DONE]`; galat di tengah stream = event `error` + `finish_reason: 'error'`; batalkan = abort |
| Reasoning | `reasoning: { effort, exclude }`; token reasoning ikut memakan `max_tokens` (bisa membuat konten kosong) sehingga diberi ruang +1024 bila diaktifkan |
| Cek key | `GET /api/v1/key` → kuota & pemakaian, tanpa memanggil model |

## Bug yang ditemukan lewat uji live: retrieval pada DB yang baru di-seed

Pada DB yang baru dibuat (`db:init` + `seed`), **semua skor FULLTEXT InnoDB bernilai 0**. Akibatnya
urutan kandidat jatuh ke `sort_order`, dan pertanyaan "gimana cara daftar jadi talenta?" mendapat
entri "verifikasi/talenta/cara kerja", bukan entri "daftar". Ini diverifikasi deterministik:
- di DB segar, skor 0 dan urutan 3, 4, 5;
- setelah `OPTIMIZE TABLE`, skor benar dan urutan 6, 5, 11.

Pemicu persisnya ada di internal InnoDB dan tidak muncul pada tabel percobaan sederhana. Inilah
skenario `demo:reset` (T16), jadi tanpa perbaikan chatbot akan salah pilih entri tepat saat demo.

Perbaikan dua lapis:
1. **`syncKbIndex()`** (`OPTIMIZE TABLE kb_entries`) dijalankan seed setelah commit. Helper ini
   juga dipakai T12/T13 saat isi KB berubah.
2. **Pemeringkatan ulang deterministik di JS** (`rankEntries`). FULLTEXT hanya menjaring kandidat
   (filter `MATCH > 0` tetap berfungsi walau skornya 0). Urutan ditentukan skor leksikal: judul 3 ·
   kata kunci 2 · isi 1, dikali bobot kelangkaan `log(1 + N/df)`, tanpa kata tanya umum. Skor
   FULLTEXT hanya pemecah seri. Hasilnya konsisten di MySQL/MariaDB, apa pun keadaan cache FTS.

Regresi: `tests/unit/kb.test.js` memakai entri KB seed asli dengan skor FULLTEXT 0 (keadaan bug).
Pertanyaan uji live harus mendapat entri "daftar", dan `searchKb` harus memakai urutan hasil
pemeringkatan ulang, bukan urutan SQL.

Catatan proses: satu uji mutasi sempat meninggalkan `chatbot.test.js` dalam keadaan termutasi,
karena `git checkout` gagal pada berkas yang belum dilacak. Berkas itu dipulihkan dari cadangan dan
dicek identik. Uji mutasi itu juga menunjukkan bahwa tes integrasi `TRUNCATE` + insert **tidak**
mereproduksi bug, sehingga tes regresinya dipindah ke tingkat fungsi (di atas).

## Catatan / sisa

- **Isi KB masih 11 entri bawaan FE lama** dan belum ada entri "cara daftar talenta". KB ≥ 25 entri
  bersumber dokumen adalah T12.
- Belum ada: intent, cache, rate limit/anggaran khusus chatbot, data pribadi, filter keluaran,
  streaming endpoint, umpan balik (semua T12); eskalasi (T13); widget FE (T14).
- **Uji MariaDB 10.4** untuk migrasi 005 belum dijalankan karena Docker Desktop tidak aktif. Semua
  pernyataannya memakai sintaks yang didukung MariaDB 10.4 (ALTER ADD/DROP COLUMN, FULLTEXT InnoDB, FK).
  Dicatat untuk T16.
- `backend/.env` repo ini **belum berisi** key OpenRouter (sesuai keputusan pengguna), sehingga
  server dev menjawab dari KB. Uji live berikutnya (T12/T13/T15) perlu izin lagi atau key diisi pengguna.
